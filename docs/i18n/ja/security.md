# セキュリティとセーフガード

Chimeraはシェルコマンドを実行し、ファイルを編集し、APIを呼び出し、自身のスキルを変更できます。**多層防御**を備えており — これが重要な点ですが — ドキュメントは各層がどこで*止まる*かを明記します。

!!! warning "唯一のルール"
    これらのセーフガードのいずれも、自律性を与える際に**隔離された環境で実行すること**の代わりにはなりません。デフォルトの `local` ランナーは隔離されていません。信頼できない作業には `CHIMERA_SANDBOX=docker`(ネットワーク遮断、オプションでgVisor下)を使ってください。

## プロンプトとボットのテキストにおけるエージェントの声

プロンプトやボットのテンプレートで、エージェントに感情・思いやり・友情・関係、または自分についての約束を
主張させてはいけません。何をしたか、何ができなかったか、どの程度確かかを述べてください。校正された一人称の
不確かさ（例：「確かではありませんが…」）は許容され、有用です。

## 各層

- **ガバナンスカーネル** — ガバナンス対象のツール呼び出しはすべて allow / warn / review / block のいずれかになります。危険なシェルシグネチャに対する安価な第一のフィルターであり、境界そのものではありません。
このファイルの省略可能な `setup` キーは、プロジェクト環境を準備するコマンドを指定します。コマンドの正確なハッシュに結び付いた所有者による個別の承認と、同じプロジェクトの有効な `shell` 許可が必要です。workspace とコマンドハッシュの組み合わせごとに最大1回実行され、失敗してもエージェントに通知するだけでターンは中断しません。承認と準備済みマーカーはチェックアウトではなく Chimera のホームに保存されます。許可と承認済みハッシュを継承するのは、登録済みプロジェクト用に Chimera が作成した永続 worktree のみです。任意の Git worktree は継承しません。アプリの worktree 登録情報は `CHIMERA_HOME` に保存されます。すでにホスト上でシェルアクセスを持つプロセスは、プロジェクト登録情報と同様にここへ書き込めます。
- **サンドボックス** — 一時的なネットワーク遮断コンテナ（`CHIMERA_SANDBOX=docker`）。gVisor（`CHIMERA_SANDBOX_RUNTIME=runsc`）で強化できます。**verifyコマンド**はエージェントのシェルと同じサンドボックスで実行されます。`.chimera/verify.toml` で宣言された検証コマンドもシェルコマンドです。隔離されていないホストでは、プロジェクトに有効な `shell` 許可があり、`CHIMERA_HOST_EXEC` がホスト実行を拒否しない場合に限り実行されます。許可がなければ棄権し、ビルドファイルから推測されたコマンドは引き続き `CHIMERA_HOST_EXEC` の確認を経て、拒否されると棄権します。プロジェクト許可は設定されたコマンドを許可しますが、ホストのサンドボックスを隔離状態にはしません（`CHIMERA_VERIFY_NETWORK=1` はDocker検証器にネットワークを与えます。カーネルサンドボックスでは不可能なため、ネットワークが必要な検証器がホストで実行されるのは、別途許可されている場合だけです）。設定とコマンドは実行可能なプロジェクトコンテンツとして扱い、シェルを許可する前に確認してください。ターン中に設定済み検証器が編集された場合、検証は棄権します。コマンドはターン開始前に取得され、初回実行前にその正確なSHA-256ハッシュに結び付いた所有者の永続的な承認が必要です（コマンド変更のたびにも再承認が必要です）。この承認が拘束するのはコマンド文字列だけで、その作用ではありません。`pytest`、`make test`、`npm test` は、エージェントが編集した可能性のある `conftest.py`、`Makefile` のレシピ、パッケージスクリプトなど、プロジェクトが制御するファイルを実行します。
- **セッションごとのツール許可リスト** — 1回の実行に必要なツールだけを許可し、残りはモデルのスキーマから完全に除外されます。
- **汚染追跡**(`--taint`) — 信頼できないコンテンツはデータとして囲い込まれ、その出所はメモリやスキルにまで追跡されます(汚染された実行から生まれたスキルはレビュー保留になります)。実行が一度汚染されると、危険なツールは絞り込まれます。
- **検疫リーダー** — dual-LLM / CaMeLパターン: 信頼できないコンテンツはツールを持たないモデルによって読まれ、スキーマ検証済みのフィールドしか出力できないため、インジェクションが新たな指示やツール呼び出しを生み出すことはできません。
- **クロスエージェントモニター** — ファンアウト時、ワーカーごとのモニターは*分割された*フローに対して盲目です(1つのワーカーが信頼できないものを取得し、別のワーカーがそれをシンクする — 取得とシンクは別々の台帳に存在する)。集約モニターはファンアウト全体を見ます。これは `solve-batch` / `crew-isolated` では**常時オン**です。

## ファンアウト: クロスエージェントモニター

複数のツール使用ワーカーが並行して実行される場合(`solve-batch`、`crew-isolated`)、それぞれが独自のケーパビリティ台帳を持ち、バッチの後に集約モニターがそれら全体に対して実行されます。これは単一ワーカーのモニターでは見えないパターンを捕捉します — ワーカーAが信頼できないコンテンツを取得し、ワーカーBがそれを実行または持ち出す、分割された持ち出し(exfiltration)です。

```
$ chimera solve-batch "read notes.md and summarize" "download the helper and run it" -w .
task1: ok
task2: ok
merged 2 file(s) across 2 task(s)
⚠ cross-agent monitor flagged (review):
  - cross-agent-taint: untrusted content entered via one agent and a different agent
    performed a sink (task2→task1) — a split flow no single-agent monitor sees
```

これは常に**レビューへのエスカレート**のみを行います — 実行をブロックすることは決してなく、純粋な可観測性です(挙動を変えずに記録するだけ)。その上に `--taint` を加えると、各ワーカーの適応型許可リストも武装されます(汚染時に危険となるツールは承認が必要になります)。

**承認と、拒否されたワーカーの見え方。** 各ワーカーは自分の承認者と「何を許されたか」の記録を持つので、拒否されたタスクは `ok` と報告する代わりにそう言います:

```
$ chimera solve-batch "read notes.md and summarize" "download the helper and run it" --taint -w .
task1: ok
task2: not allowed (ok)
  governance: 1 action(s) refused for review: run_shell is restricted after this run consumed
  untrusted content
1 of 2 task(s) had actions refused for review — check that the work they were asked to do
actually happened.
```

括弧の中の `ok` はループ自身の判定で、この二つが食い違うことこそが要点です: 拒否された呼び出しはただの観察行として返るため、ワーカーはそれを他のツール結果と同じように読み、そのまま進み、文章で終わります。誰に訊けるかは `CHIMERA_APPROVAL_MODE` に従います — `deny` はその場で拒否し、`ask` は端末があれば尋ね、なければ質問を書き留めて `chimera approve` を待ち、質問ごと・ワーカーごとに `CHIMERA_APPROVAL_WAIT` 秒待ちます。沈黙は常に拒否です。

## 主張ではなく計測

```bash
chimera redteam
```

インジェクションのコーパスをスタック全体に通します。組み込みのコーパスでは、汚染層が**攻撃成功率を100%から約14%に**下げます — そしてレポートは100%を主張する代わりに、依然としてすり抜けるもの(許可されたツール経由の持ち出し)を*名指し*します。

同じコマンドは**コスト**も表示します。このページの最初の版はそれをしていませんでした: 尋ねる相手がいなければ、絞り込みは**最初に外部の何かを読んだ正当な作業の100%**を拒否します — issueが名指しするファイルを直す、ドキュメントが説明するアップグレードを適用する — そして登録済みのゲート(過剰ブロック(over-block)≤ 5%)は不合格になります。この数字はチューニングの問題ではありません。ゲートが空だったのです。デフォルトの承認モードは `ask` であり、デスクトップでは実際に尋ねるようになりました: 絞り込まれたツール呼び出しは、台帳の理由を添えた画面上の質問になり、ボタンか `chimera approve` で答え、`CHIMERA_APPROVAL_WAIT` 秒の沈黙によって拒否されます。人が自分で頼んだ作業を承認するなら、過剰ブロックは0%になり、攻撃のブロック率は動きません — 腕ごとに計測した結果は
[`bench/injection/RESULTS.md`](https://github.com/brcampidelli/chimera-agent/blob/main/bench/injection/RESULTS.md)にあります。許可されたツール経由の持ち出しも同じ変更で塞がれます: 汚染された実行の `http_get` がクエリ文字列を伴う場合はレビューとなり、コーパスに追加された2件の正当なクエリ文字列付きGETが、その代償を示します。

### 実行をまたぐ、毒されたメモリ

`redteam` は1回の実行を計測します。もう一つの形はもっと遅く、1つのプロセスには収まりません: 実行Aが毒されたページを読み、「学んだ」ことを保存する。数日後、実行Bが無関係な質問をし、想起が植え込まれた事実をモデルに手渡す。

```bash
chimera memory-poison
```

これもオフラインで無料です。この2つの実行の間に立つ3つの層 — `tainted` という出所フラグ、想起の受理ゲート、そして事実がプロンプトへ入るときにまとう `[unverified]` ラベル — をアブレーションします。単一の数字では、そのどれが何もしていなくても辻褄が合ってしまうからです。見出しになるのは**印のないまま**届くものであって、ブロックされるものではありません: 出所を帯びた毒された事実は、モデルが警告を受けている事実です。ラベルのないものは、エージェント自身が検証したものと見分けがつきません。

最初の実行から2つの結果を、はっきり述べておく価値があります。どちらもこちらを良く見せるものではないからです:

- **出荷される構成は、自らのゲートに — コストで — 不合格になります。** 毒の100%に印を付け、その代償として正直なメモリの25%を破壊します。犠牲者には名前があります: 攻撃を説明するためにそれを引用しているセキュリティ文書と、試みを転送しているサポートチケットです。コンテンツに対するパターンマッチャーは、引用と命令を区別できません。
- **このコーパスでは、コンテンツのゲートは出所ラベルがすでに覆っている以上のものを何も足しません。** 計測されたその効果のすべては、それが取り除く正直なメモリです。手で書かれた15行は指針であって判定ではなく、だからこそそれを根拠に何も削除してはいません。

しきい値、手法、そしてこれらの数字が*許さない*ことは、最初の実行の前に確定された
[`bench/memory_poison/PREREGISTRATION.md`](https://github.com/brcampidelli/chimera-agent/blob/main/bench/memory_poison/PREREGISTRATION.md)にあります。

## HTTPサーバーの公開

`chimera serve` はデフォルトで `127.0.0.1` にバインドされます。その状態変更エンドポイント(`/chat`、`/a2a`、`/webhook/*`)はエージェントを駆動するため、**サーバーをネットワークに公開する前に**、ベアラートークンを設定してください。

```bash
export CHIMERA_SERVER_TOKEN="a-long-random-secret"   # required as: Authorization: Bearer <token>
```

これを設定すると、それらのPOSTエンドポイントは一致する `Authorization: Bearer` ヘッダーがない場合 `401` を返します(`GET /health` とA2Aのagent-cardは公開されたままです)。WhatsAppの受信webhookについては、`CHIMERA_WHATSAPP_APP_SECRET` にMetaアプリのシークレットを設定してください — するとChimeraは各リクエストの `X-Hub-Signature-256` HMACを検証し、偽造されたペイロードを `403` で拒否します。どちらもオプトインです(未設定 = 認証なし、localhostなら問題ありません)。公開デプロイでは設定するべきです(または認証プロキシの背後に置いてください)。

### 会話を第二の人と共有する

デスクトップアプリは、**その会話だけを開くトークン**でコーディング会話を共有できます — サーバートークンは決して使いません。
所有者はゲストごとに1つ発行し（`POST /api/code/sessions/{id}/share`）、個別に失効させられます。会話を削除するとすべて失効します。
ゲストは `/guest/api/…` 配下の4つのルートに到達します：会話を読む、ライブで追う、メッセージを送る、誰がいるか見る。
共有トークンで他に応答するものはなく、ゲストアプリにはガバナンスカードに答えるルートがありません — それは所有者の画面に残ります。

所有者がネットワークの扉を開いたとき（`POST /api/code/share/network`、`DELETE` で閉じる、起動時に開くことはない）、
提供されるのもゲストアプリ**だけ**です：LAN 上のマシンはこの4つのルートに到達し、サーバートークンが守るものには到達しません。
リンクを渡す前にはっきり言っておくこと：ゲストは所有者が頼めることなら何でもエージェントに頼めます。所有者のプロジェクトで、
所有者のツールと費用で — リクエストの既定の制約のもとで、カードの承認はできません。

### 自分のスマートフォンやブラウザ：デバイスのペアリング

ゲストリンクは他の誰かのためのものです。所有者が自分のスマートフォンで使うにはペアリングがあります：`chimera pair`（または 設定 › アクセス の **デバイスをペアリング**）は、**1回だけ、5分間**有効なコードを、ペアリング用アドレスの QR とともに表示します。
コードは2つ目の LAN リスナーが提供するページに入力します — このリスナーは起動のたびに閉じられ、所有者だけが開きます（`chimera pair --lan`、またはカードの **開く**）。
入力すると30日間の cookie（`HttpOnly`、`SameSite=Strict`、https では `Secure`）になり、所有者のデバイス用シークレット（`<home>/devices.key`）から導出した鍵で署名されます。
誤ったコードが5回入力されると有効なコードはすべて無効になり、同じアドレスから5回なら、そのアドレスは15分間締め出されます。

ペアリングしたデバイスは**読むことと話すこと**について所有者です：会話、ターン、ガイダンス、エージェント自身の質問への回答、そして承認の拒否。所有者の画面ではありません。
承認には引き続き各質問のコードが必要で（研究 30、S30-30）、アクセスを発行する、設定を変える、フォルダを許可する、ボットを起動する、サービスを停止するルートは、デバイスに `403` を返します。
アクセスカードはすべてのデバイスを最終使用とネットワーク（`192.168.1.x`）とともに一覧表示します。**取り消す** は1台を即座に終了させ（開いているライブストリームも含む）、**すべてのデバイスを取り消す** はシークレットを置き換えるので、それ以前に発行された cookie はどれも検証を通りません。
デスクトップのブリッジは、ペアリングも、コードの発行も、一覧表示も、取り消しもできません。

外出先のために、Chimera は**独自のリレーを一切動かしません**。外からデバイスリスナーに到達したいなら、自分で管理するトンネルをその前に置いてください — 両方のデバイスに [Tailscale](https://tailscale.com/)、または `http://127.0.0.1:<port>` への [Cloudflare Tunnel](https://developers.cloudflare.com/cloudflare-one/connections/connect-networks/) — そして、それを意識して決めてください：トンネルが届く先まで同じ扉を延ばすことになります。
このためにアプリ自体を `0.0.0.0` にバインドしてはいけません。

## デスクトップアプリのバックエンド

アプリのバックエンドは loopback で待ち受けますが、loopback は人ではありません：マシン上のどのプロセスもそのポートに到達できます。

- **すべてのルートにトークン。** デスクトップアプリは常に bearer トークン付きでバックエンドを起動します — 起動ごとの新しい秘密値か、所有者がすでに設定した `CHIMERA_SERVER_TOKEN` です。
  するとすべての `/api/…` ルートは、それがなければ `401` を返します（`/api/health` も含む）。開いたままなのはアプリの静的ファイルとゲストアプリ（`/guest/api/…`、自分の共有トークンを自分で検査する）だけで、
  MCP ブリッジ（`/api/bridge/…`）は自分のトークンを持ち続けます。シェルは起動ごとのトークンを、バックエンドには環境変数で、ウィンドウには webview の初期化スクリプトで渡します — コマンドライン、URL、ファイルには決して載せません。
  バックエンドが起動するものはそれを継承しません：サンドボックスの子プロセスの環境と、`gh` と `git` が動く環境は、秘密らしい名前の変数をすべて落とします（`GH_TOKEN` など gh 自身の資格情報は例外）。
- **コードなしの承認には画面が要る。** トークンが示すのは誰が API を呼べるかであって、所有者が見ていることではありません。コードなしの「はい」（`POST /api/approvals/{id}`）が通るのは、
  リクエストが bearer トークンに加えて `X-Chimera-Screen` に画面資格情報を載せているときだけです。これは起動ごとに生成されてメモリにだけ置かれます：ファイル、レコード、ログ、`.env`、ルートの応答には決して入らず、
  bearer トークンと同じ値は拒否され、読み取った時点で環境から取り除かれます（シェルは `CHIMERA_SCREEN_TOKEN` として渡します）。ディスクから読めるトークン — `service.token`、`.env` の `CHIMERA_SERVER_TOKEN` — は、
  「はい」には引き続き質問ごとのコードが必要です。拒否にはコードは要りません。`chimera service` は画面資格情報を持たないので、そこではすべての「はい」がコードを求めます。ブラウザで使う `chimera app` は、
  loopback のリクエストに返すページ（`<meta name="chimera-screen">`）にそれを入れます — そのページがすでに bearer トークンを載せているのとまったく同じ場所と条件で、つまり露出は同じです（2026-10-16 の所有者の決定）。
- **バックグラウンドサービス。** `chimera service start` は同じバックエンドをウィンドウなしで動かします。`~/.chimera/service-<channel>.json`（0600、アトミックに書き込み。`CHIMERA_SERVICE_DIR` で場所を変更可）を、
  所有者の永続トークン（`<home>/service.token`、または所有者が選んだ `CHIMERA_SERVER_TOKEN`）とともに公開し、クライアントは `GET /api/info` が同じ pid、バージョン、id、データフォルダーを返して初めてそのファイルを信頼します。
  このトークンは API 全体を開くので、ブリッジのトークンとは分けておかれます：MCP 側の何ものもサービスのファイルを読まず、ブリッジはそれらをファイルとして拒否します。インストール済みアプリの起動レコード
  `~/.chimera/desktop-install.json` には4つのパス変数 — `CHIMERA_HOME`、`CHIMERA_WORKSPACE`、`CHIMERA_SHELL_PREFS`、`CHIMERA_SHELL_STATE` — しか入らず、書き込み側はそれ以外の名前を拒否し、`start` はそこから何かを実行する前に検証します。

### ブリッジ経由のフルコントロール

デスクトップブリッジ（`chimera mcp desktop`）には三つのスイッチがあり、それぞれ前のスイッチなしでは意味を持ちません：**Claude にこのアプリの操作を許可**、**フルコントロール**、そして 2026-10-18 の所有者の決定以降は 設定 > セキュリティ の **ブリッジ経由のフルコントロール** です。

- **オンにできるのは画面だけ。** `CHIMERA_BRIDGE_FULL_CONTROL` は編集可能な設定の一覧にないため、`PATCH /api/config` は誰に対しても拒否し、ブリッジの `settings.edit` も名前で拒否します。唯一のルート `POST /api/security/bridge-full-control` は、ブリッジが転送したリクエストをすべて拒否し、画面の資格情報があるときだけオンにします。所有者のトークンだけではディスク上で読める `service.token` にすぎません。画面は確認を求めます。オフは狭めるだけなので画面は不要です。
- **加わるもの。** 所有者の決定（フォルダーでのコマンド許可、ツール付きのエージェントの保存、記憶された承認ルール、一括拒否、プロジェクトの記憶、設定提案への回答、プラグインとマーケットプレイス、worktree の整理）、本人の `confirm: true` を必要とするルート（デザインの復元・削除・エクスポート、ストレージの整理、再起動とリセット）、所有者の設定 — ポスチャ、ガード、承認、上限、モデル、スケジュール（提案ではなく書き込み）— 、そしてアプリの画面を開くこと（`ui.navigate`。アプリ自身の画面と照合されるアドレスで、URL は不可）。
- **決して加わらないもの。** 資格情報：鍵、トークン、パスワード、OAuth のシークレットは読み書きされません。Runner、MCP サーバーの追加やサインインは所有者のもので、鍵の保管庫、エージェントによる `.env` の読み取り、プロバイダーのベース URL は書き込めません。そしてアプリに誰が到達できるか：デバイスのペアリング、共有、LAN のドア、サーバートークン、ボットとその許可リスト。
- **カーネルが先に決める。** 承認は REVIEW に答えるもので、カーネルの BLOCK は承認者に届きません。実行ごとのチェックは残り、ブリッジが始めた実行は設定済みのモデルとポスチャを使います。
- **見えて、記録される。** オンの間はすべての画面にワンクリックの **オフにする** 付きのバーが表示され、この権限で行われた呼び出しはすべて監査エントリ（`via: "bridge"`、`scope: "full_control"`、ルート、ステータス、ID のみ。本文や値は記録しない）として書かれ、セキュリティ タブに一覧表示されます。
- **正直な限界。** スイッチは他の二つと同じく `.env` にあります。そのファイルを書けるプロセスは画面なしでオンにできます。エージェントのツールとブリッジはこのファイルを拒否しますが、所有者として動くそれ以外のものは拒否しません。

## 所有者が決めること、リポジトリにはできないこと

- **デプロイメントポリシー、禁止のみ。** `<CHIMERA_HOME>/policy.json`（または `CHIMERA_POLICY_FILE` が指すファイル）には順序付きの `provider.use` / `integration.use` / `tool.use` ルールが入り、最後に一致したものが決めます。
  そこでの `allow` は何も許可しません：同じファイルの先行する deny を取り消すだけなので、`CHIMERA_TOOL_DENYLIST`、到達範囲の床、カーネルの BLOCK を開き直すことはできません。不正なファイルが部分的に適用されることはありません：
  `serve`、`chat`、`assist`、`tui`、`acp` は起動を拒否し、`doctor` は失敗し、デスクトップは起動しますが修正されるまですべてのツールを拒否します。エージェントはそれを書き換えられません — 書き込みツールはそのファイルがどこにあっても拒否し、ブリッジはその向き先を変えられません。
- **「このプロジェクトでは常に」。** 承認カードで所有者は、あるプロジェクトについて「はい」を記憶させられます：ツール単位、シェルコマンドなら最初の2語です。以後一致する質問に答えます。**実行が信頼できない内容を読んだ後でも** —
  敵対的なページがその接頭辞の中でコマンドを操れると承知のうえでの、2026-10-15 の所有者の決定です。省くのは質問だけです：カーネルの BLOCK と到達範囲の床は引き続き優先し、連結・パイプ・リダイレクトするコマンド（`;`、`&&`、`|`、`>`、`$(`…）は決して一致しません。
  作成も取り消しも所有者だけができ、ブリッジにはできません（所有者がブリッジ経由のフルコントロールをオンにした場合を除く。上記参照）。
- **名前付き参照。** 所有者が `<CHIMERA_HOME>/references.json` に列挙したフォルダーは、読み取りツール（`read_file`、`list_dir`、`grep`、`glob`）からだけ `@alias/path` として到達でき、書き込みツールはすべてエイリアスを拒否します。
  ファイルシステムのルート、ユーザーのホーム、データフォルダーは参照として拒否されます。受け取るのは人が付いているサーフェスだけ — `chat`、`assist`、`tui`、人が付いている `solve`、デスクトップの Code ターン（ゲストのものは除く） — なので、ボット、cron、`scenarios` には参照がありません。
- **Markdown のエージェント。** リポジトリの `.chimera/agents/*.md` は他人の書いたテキストなので、狭めることしかできません：ツールはセッションの統治されたツールと交差され、ステップ数はセッションのもので上限が付き、未知のキーは拒否され、`model` は無視され、
  本文は信頼できないデータとして囲われます。カタログのモデルを固定できるのは `<CHIMERA_HOME>/agents` にある所有者のファイルだけです。
- **会話に結び付けたチャット。** Discord や Telegram で `/link` を使うと、チャットが Code の会話の続きになります。結び付けられるのはそのボットの allowlist に載った所有者だけで、allowlist がなければ誰もできません。
  結び付けたルームでの他人のテキストは決して会話に届かず、メディアは転送されずに拒否されます。ターンはデスクトップではなくボットの床で動きます：`CHIMERA_BOT_MCP_SERVERS` の MCP サーバーだけ、OpenAPI コネクターなし、シェル許可も host exec もなし。
- **所有者のコネクターは、他人が開けられる扉から遠ざけられる。** OpenAPI コネクターは所有者のキーで外部を呼ぶので、実行を動かしている人に答えることになります。設定済みのボットのどれかに allowlist がない間はメッセージング系のサーフェスでは読み込まれず、
  GitHub の issue ジョブでは決して読み込まれず（issue は誰でも書け、検査されるのはリポジトリだけ）、`/v1/chat/completions` では `CHIMERA_SERVER_TOKEN` が設定されている間だけ読み込まれます。名前がどの種類のサーフェスかは1つのモジュール
  `chimera/governance/surfaces.py` がファミリーで決め（`platform:discord` はボット）、どこかのモジュールが再び独自のリストを書けばテストが失敗します。

## 正直な限界

これは*すでにインジェクションされた*エージェントの有害な行動が止められるかどうかを計測するものであり、そもそもモデルがインジェクションされうるかどうかではありません。信頼できない文章に対する自由形式の推論、そして正当に必要なツールを通じた持ち出しは、未解決の問題として残っています([issue #5](https://github.com/brcampidelli/chimera-agent/issues/5)で追跡)。

完全で常に最新のポリシーは
[SECURITY.md](https://github.com/brcampidelli/chimera-agent/blob/main/SECURITY.md)にあり、脆弱性の報告方法も含まれています。

## セッション権限バイパスの限界

任意のコードセッション権限バイパスは、プロセスメモリ内で生成された HMAC キーで認証されます。このキーがディスクに書き込まれたり、子プロセスに継承されたりすることはありません。有効な HMAC のない永続化された `bypass_permissions` フラグやキュー内の `via_screen` 証明は無視されます。そのため権限の選択はアプリ／サービスのプロセス再起動までしか続かず、再起動後はバイパスが既定で無効になります。シェルから JSON を編集することはできますが、証明を偽造することはできません。字句的な停止規則は、検出された Git push、パッケージ／コンテナーの公開、特定の GitHub API 変更、秘密ファイルの既知トークン（`.npmrc`、`.netrc`、`.pypirc`、`.git-credentials`、AWS 認証情報など）、特定の HTTP アップロード／データオプションやリモート `rsync`／`scp` 宛先を拒否します。これはヒューリスティックでありセキュリティ境界ではありません。`cat .e*` のような glob 展開された名前、`python -c "open('.'+'env')"` のような動的に組み立てた文字列、別のエンコード、ラッパー、認識された構文以外のコマンドは検出を保証できません。悪意あるページは依然として回避できます。信頼できない作業には隔離サンドボックスを使ってください。
